# 节点质量分级设计

更新：2026-11-14。状态：**已实现并上线**（迁移 `0018_entry_probes_grading`、`0019_grade_exclusions`）。第 9 节的问题用户已于 2026-11-13 决定（接受只发入口 IP、覆盖旧的大陆参考决策、注册一个 Globalping 账号、默认三网视角、界面移除 P 等级与线路声明）。下文第 2–8 节是设计稿；与实际实现不同之处以第 0 节为准。

## 0. 实现与设计的差异

- **计算位置**：等级在 Python（`app/grading.py`、`app/probes/refresh.py`）计算后写入 `node_grades`，SQL/Worker 只读；没有 `entry_probe_targets`/`entry_probe_summaries` 表，计划器每小时从 `entry_probe_results` 的 SQL 聚合读取历史。
- **Cloudflare 入口**（2026-11-14 起）：只用三网探针测 CF 任播边缘（反映各运营商到 CF 的接入）。香港/新加坡探针只能连到本地 CF 机房（约 1 ms），不代表节点，因此不测；已有的这类样本在定档时忽略，港新视角显示“接入未测，最高 B”并给出原因。此前这一份 1 ms 样本曾被套用到约 1,600 个 CF 入口节点上。
- **Cloudflare 落地**（2026-11-14 起，用户决定“不需要 CF 的落地”）：落地 ASN 为 13335 的节点不发起接入测量、不定档。迁移 0019 让“当前可用但没有等级行”的节点显示为“不分级”（NULL），不再算作待定；它们不进入等级筛选、按等级排序和每台服务器取最佳。每日检测照常进行，落地 ASN 只能由每日检测得知；节点本身不自动停用。
- **港新探针**（2026-11-14 起）：使用 `eyeball-network`（家宽）探针，香港和新加坡各自单独测量、各自记录上次时间（家宽探针偶尔自身运行失败，合在一次测量里会让另一地区的新样本每小时被重复购买）；当时没有在线家宽探针（Globalping 返回 422）时退回该地区任意探针。家宽标签只是减少机房读数，个别标为家宽的网络（如 AS61112）实际是机房，仍可能测出 1 ms。机房探针到同城机房的节点会测出 1–2 ms，数值真实但不代表家宽用户；旧样本 7 天内自然过期。

**原则（用户 2026-11-13 确认）：只记录能实测证明的东西。** 推断、机场自称、数据库猜测都不作为结论；界面上的每个标签都要能指出是哪次测量得出的。本文只使用聚合数字，不含任何节点 IP、域名或订阅信息。

## 1. 目标

把大量可用节点分成 S/A/B/C/D 几等，回答“从**中国大陆（电信/联通/移动）、香港、新加坡**的网络连这个节点，好不好用”。等级要能解释（每个等级附理由），可筛选、排序、导出，并且与 Python / Worker / SQL 三端一致。

不做：下载测速、带宽测试、网段扫描、本机测量（用户已排除），以及任何外部无法证明的结论：IPLC/IEPL 专线判断、BGP 推断回程、按节点名称识别线路（`line_type` 仍为 UNKNOWN）。

结论：

1. **现有数据完全没有 CN/HK/SG 视角。** HTTPS 耗时是“美国 Runner → 入口 → 落地 → Cloudflare Echo”，跟大陆用户的体验基本无关；旧的 P1/P2/P3 只是理论候选。
2. `runner_node_summaries` 按 `probe_key`（Runner 国家+ASN）分开，Runner 会变，导致单个 probe_key 很少攒够样本。稳定性应改用跨 Runner 的日统计（`nodes.checked_days/available_days`、`node_daily_stats`）。
3. 才 3 天数据，稳定性需要“资料不足”档，不然一天好运就能进 S。

## 3. 两层模型

节点质量拆成互相独立的两半，按各自的“归属单位”测量：

| 层 | 回答什么 | 归属单位 | 数据来源 |
| --- | --- | --- | --- |
| **接入层**（入口） | 从某地区某运营商连得上吗、延迟/丢包/抖动/晚高峰劣化如何 | 入口 IP:端口 | **新增**：第三方探针 TCP ping（第 4 节） |
| **本体层**（节点+落地） | 节点是否真的能代理、是否天天稳定、落地 IP 什么类型 | 节点；落地服务器 | 现有 Actions 完整检测 + ip-api |

同一个入口从 HK 可能极好、从移动可能很差，所以**等级按地区分别计算**：`CN-CT`、`CN-CU`、`CN-CM`、`HK`、`SG`，再加一个 `CN`（三网综合，取三网中的最差档）。用户在设置里选默认地区（例如“我用电信”），列表默认按它显示，也可以切换。不做一个混合所有地区的总分：那个数字没有意义。

## 4. 接入层数据：Globalping 社区探针

### 4.1 为什么选它

[Globalping](https://globalping.io) 是 jsDelivr 运营的免费公开测量网络，有 API，GitHub Actions 可以直接调用，符合“严格免费、不用自有服务器”。2026-11-13 在线探针（`/v1/probes`）：

| 地区 | 探针数 | 说明 |
| --- | --- | --- |
| CN | 40 | 其中家宽（`eyeball-network`）约 24 个：电信 AS4134 ×5，联通 AS4837/17621/9929 约 10 个，移动 AS9808/56041/560xx 约 9 个；其余为阿里/腾讯/华为云 |
| HK | 118 | 机房为主，含 HKT、HKBN、HGC 等本地宽带 |
| SG | 167 | 机房为主 |

API 规格（[schemas.yaml](https://github.com/jsdelivr/globalping/blob/master/public/v1/components/schemas.yaml)）：`ping` 支持 `protocol: TCP` + `port`，每次最多 16 个包（返回 min/avg/max/mdev 及丢包）；位置可按国家、ASN、`eyeball-network` 标签组合筛选。

限额（[spec.yaml](https://github.com/jsdelivr/globalping/blob/master/public/v1/spec.yaml)）：匿名每小时 250 次测试，注册用户（免费 token）每小时 500 次；**1 次测试 = 1 个探针执行 1 次测量**，与包数无关，所以每次都发 16 个包。

### 4.2 它能证明什么、不能证明什么

能证明：在某个时刻，从该运营商的一台真实家宽探针，到入口 IP:端口的 **TCP 握手**成功与否、RTT、丢包、抖动。大陆最常见的封锁方式是封 IP 或 IP:端口，在这里会表现为三网全部握手失败，而美国、香港仍然正常。

不能证明：
- 代理协议本身能过墙。TCP 握手成功后，TLS/代理流仍可能被重置或限速（协议特征识别、SNI 阻断），这类问题测不到。
- 带宽、线路类型（IPLC/CN2 等）。
- 用户自己网络的情况。家宽探针数量少，而且会上下线。

因此界面标注为“**大陆 TCP 实测（第三方探针）**”，不写成“大陆可用”。`mainland_reachability` 改为记录这个 TCP 结论，`line_type` 不变。

### 4.3 特殊入口

- **Cloudflare 入口**（1,638 个可用节点）：TCP ping 测到的是 CF 任播边缘，不是节点本身。按 CF 入口 /24 段只测少量代表 IP，结果作为“CF 中转”一类共享，不逐节点消耗额度。
- **Hysteria2**（UDP/QUIC）：TCP ping 没意义。改为 ICMP ping 入口 IP，结果标“ICMP 估计”，最高评到 A。
- **仅 IPv6 入口**：探针 IPv6 支持情况不一，先标“未测”。

### 4.4 测量计划与额度

免费注册额度为每小时 500 次，即每天约 12,000 次。**不能按节点测**（8,434 个可用节点 × 5 个地区 = 42,000 次/轮），要按“网段”分层测。2026-11-13 的只读统计（可用节点、IPv4、非 Cloudflare 入口）：6,577 个节点 → 2,196 个入口 IP → 2,752 个 IP:端口 → **1,726 个 /24 网段**；Cloudflare 入口 1,364 个节点，分布在 356 个 /24；仅 IPv6 或无入口 IP 的 493 个。

分层依据：线路质量（延迟、绕路、晚高峰拥塞）由 BGP 路由决定，同一个 /24 的路由基本相同，只测一个代表就够了；封锁可能精确到 IP:端口，所以要逐个查，但封锁是全国性的，任意一个大陆探针测一次就行。

| 测量 | 单位 | 每轮次数 | 频率 | 日均 |
| --- | --- | --- | --- | --- |
| 大陆阻断检查 | IP:端口，任一大陆探针 1 次 | 2,752 | 2 天一轮 | ~1,400 |
| 三网晚高峰线路 | /24 代表，电信/联通/移动各 1 次 | 5,178 | 见下 | ~1,500（受晚高峰窗口限制） |
| 三网空闲时段线路 | 同上 | 5,178 | 3–4 天一轮 | ~1,500 |
| HK / SG | /24 代表，各 1 次 | 3,452 | 2 天一轮 | ~1,700 |
| Cloudflare 入口 | 约 10 个代表 IP × 5 地区 | 50 | 每天 | 50 |
| 三网去程路由（4.5） | /24 代表，三网各 1 次 mtr | 5,178 | 每月一轮 | ~170 |
| **合计** | | | | **约 6,300 / 12,000** |

**真正的瓶颈是晚高峰窗口**，不是全天总量：北京时间 20:00–23:00 只有 3 小时，最多 1,500 次。要让每个 /24 一周内每家运营商有 2 个晚高峰样本，需要每晚约 1,480 次，正好顶满。缓解办法（可叠加）：

- 晚高峰放宽到 19:30–23:30（4 小时约 2,000 次）。
- 空闲时段已经是“差”（丢包 > 10% 或 RTT > 300 ms）或已判定阻断的网段，不再占晚高峰额度：晚上只会更差。
- 已有足够样本、结果稳定的网段降到每周 1 个晚高峰样本；新网段和订阅方案里的网段优先。

按现在的规模，免费额度够用，但余量只有约一倍。节点再翻倍时，晚高峰窗口会先不够，只能缩小范围（只覆盖订阅方案里用到的网段），或按条款第 6 条向 Globalping 申请提高限额。

其他规则：

- **只测“美国完整检测当前可用”的节点**；从未测过的 > 结果过期的 > 订阅方案里的 > 其他。
- **样本要求**：7 天滚动窗口内，每家运营商至少 2 个**不同探针**的晚高峰样本，取中位数；不足就是“资料不足”。家宽探针少（电信约 5、联通约 10、移动约 9），轮换使用并记录探针 ASN 和城市。
- **独立工作流** `entry-probe.yml`（每小时一次，晚高峰时段加密），不放进 daily-check。只是等 HTTP 结果，CPU 很少；公开仓库不计 Actions 分钟数。
- **只用一个注册账号的 token**，不叠加匿名额度，不开多个账号或多个 Runner 换 IP。[使用条款](https://globalping.io/terms/terms-of-use)第 5 条禁止用额外账号/IP 规避限额，第 13 条可封账号和 IP；第 6 条允许正当项目申请提高限额。没有 token 时可以退回匿名模式（每 IP 每小时 250 次），两者不同时使用。
- 额度以外的途径：托管探针每天 +150 次（可以忽略）；赞助 $1 = 4,000 次（不符合“严格免费”，只列出供参考，[来源](https://globalping.io/credits)）。

### 4.5 线路：只记录实测的去程路由

Globalping 的 `mtr` 支持 TCP 模式和端口，每一跳都返回 IP 和 ASN（[schemas.yaml](https://github.com/jsdelivr/globalping/blob/master/public/v1/components/schemas.yaml)）。从三网家宽探针各追踪一次到入口，记录**去程（国内 → 入口）实际经过的骨干网**：

| 运营商 | 记录的事实（按经过的 ASN） |
| --- | --- |
| 电信 | 是否经过 AS4134（163）、AS4809（CN2），以及先后顺序 |
| 联通 | 是否经过 AS4837（169）、AS9929、AS10099 |
| 移动 | 是否经过 AS9808 / 省网 AS560xx（CMNET）、AS58453（CMI）、AS58807（CMIN2） |

显示为“电信去程：经 AS4809（2026-11-20 实测）”这样的事实，**不翻译成**“CN2 GIA”“精品网”等线路名，因为线路名还涉及回程，而回程从国内测不到。

明确不做：
- **回程**：由服务器商决定，只能靠 BGP 公开数据推断，属于外部无法证明，不做。
- **IPLC/IEPL 专线**：专线在中转商内部，外部看和公网中转一样，不做任何判断或标签。
- **节点名称里的“专线/IEPL/GIA”**：只是机场自称，不提取成标签（原名称照常显示）。

另外记录**入口和落地的位置**（入口 GeoIP 与 Echo 实测的落地国家/ASN 都已有），只写“入口 CN AS56040 → 落地 HK”这样的事实，不写“中转”“专线”。2026-11-13 可用节点中入口在大陆的有 27 个，入口与落地不同国家的 1,493 个（含 Cloudflare 入口）。

路由几周才变一次，每个 /24 每月测一轮即可，约 5,200 次/月。线路信息只做展示和筛选，**不参与定档**，定档只看晚高峰实测的 RTT、丢包和稳定性。

## 5. 评分规则

### 5.1 先过硬门槛（任一不满足就直接定档）

| 条件 | 结果 |
| --- | --- |
| 当前不是新鲜 UP、资产停用或失去有效来源 | **D 不可用** |
| 该地区所有探针 TCP 握手全失败（跨 ≥2 个时段、≥2 个探针），而美国/其他地区正常 | **D 该地区 TCP 不通**（只陈述事实，不写“被墙”这一原因推断） |
| 稳定性样本不足（已检测天数 < 3）或接入样本不足（4.4 的要求） | **待定**（显示已有数据，但不给 S/A） |

### 5.2 接入档（按地区；用晚高峰中位数，HK/SG 用全天中位数）

| 档 | CN 三网 | HK / SG |
| --- | --- | --- |
| 优 | RTT ≤ 80 ms，丢包 ≤ 1%，抖动 ≤ 15 ms，晚高峰 RTT 比空闲涨 ≤ 30% | RTT ≤ 30 ms，丢包 ≤ 0.5% |
| 良 | RTT ≤ 150 ms，丢包 ≤ 3% | RTT ≤ 80 ms，丢包 ≤ 2% |
| 中 | RTT ≤ 250 ms，丢包 ≤ 8% | RTT ≤ 180 ms，丢包 ≤ 5% |
| 差 | 其余 | 其余 |

档位用**绝对阈值**而不是百分位，这样节点池变化时档位不会漂移。所有阈值存进 `quality_policies`（沿用现有版本历史和 `expected_version` 冲突保护），可在设置页调整。

### 5.3 本体档

- **稳定性**：最近 7 天日可用率（可用天数 / 检测天数，未检测日不进分母）。≥ 95% 优，≥ 80% 良，≥ 60% 中，否则差。
- **落地 IP 类型**作为标签，不进入等级，并注明来源“ip-api 标记”（这是第三方数据库的分类，不是实测）：家宽 / 移动 / 机房 / proxy 标记。ip-api 的 proxy 标记很宽（约一半可用节点都有），用它降级会误伤。需要“干净落地”的用户可以单独筛选这个标签；policy 也可以选择“S 要求无 proxy 标记”，默认关闭。

### 5.4 等级：短板决定

| 等级 | 条件 |
| --- | --- |
| **S** | 接入优 + 稳定优 |
| **A** | 接入 ≥ 良 + 稳定 ≥ 良 |
| **B** | 接入 ≥ 中 + 稳定 ≥ 中 |
| **C** | 当前可用，但接入差或稳定差 |
| **D** | 不可用 / 该地区 TCP 不通 |
| **待定** | 资料不足 |

用“取较差一项”而不用加权总分，一眼就能看出卡在哪一项，理由也好写（例如“A：联通晚高峰 RTT 132 ms（良），7 天可用 7/7（优）”）。同一等级内部按连续分数排序：接入 RTT、丢包、稳定性归一化后的加权分，只用于排序，不用于定档。

等级是**绝对的**：从大陆用美国节点，难到 S 是正常的。为了在每个落地地区里也能挑出最好的，同时显示“同落地地区排名”（例如“US 内前 5%”），按落地国家筛选时可以直接按它排序。

### 5.5 按落地服务器汇总

很多节点共用一个落地服务器（2,119 个落地 IP 对应 8,434 个节点）。节点页的“按落地服务器”视图显示每台服务器的最佳等级和最佳入口，例如“这台服务器：电信最好的入口是 X（S），移动最好的是 Y（A）”。导出时可以选“每台落地服务器只保留最佳节点”，避免订阅里塞满同一台机器。

## 6. 前端改动

源文件都在 `app/web/js/`（不要只改 dist）。下面按页面列出改动，原则同上：界面上只出现实测数据，每个数字都要标明从哪里测的。

### 6.0 全局：视角（看哪个地区的等级）

- **视角** = `CN-CT 电信 / CN-CU 联通 / CN-CM 移动 / CN 三网 / HK / SG`。默认值存在设置里（新 policy 字段 `default_vantage`），节点页和总览页标题旁有一个分段切换，切换结果写进 URL 参数 `vantage=`，可以分享、刷新后保留。
- 所有“等级”“晚高峰延迟”“丢包”都跟随当前视角。徽章旁边固定写视角，例如“A · 电信”，避免截图脱离上下文后被误读。
- 等级徽章：S / A / B / C / D / 待定，始终显示字母，不只靠颜色。颜色沿用现有色板：S 新增强调色（`--grade-s`，浅色和深色主题各一份），A `--ok`，B `--info`，C `--warn`，D `--bad`，待定 `--mute`。放在 `core.js` 的新 `gradeBadge(grade, vantage)` 里，和现有 `badge()` 同风格。
- **数据量**：切换视角会重新拉一次精简列表。38k 节点约 9 MB，按 Neon 每月 5 GB 网络传输，频繁切换会吃额度。所以默认视角放在设置里，日常不需要切换；精简列表只带当前视角的数值，不把 6 个视角都带上。

## 7. 实现要点

- **迁移 `0018_entry_probes_grading`**：
  - `entry_probe_targets`：目标键、类型（TCP/ICMP/CF 类）、优先级、上次测量时间。
  - `entry_probe_results`：目标、地区、探针 ASN/城市/标签、时间、是否晚高峰、发送/收到包数、RTT min/avg/max/mdev、measurement ID。
  - `entry_probe_summaries`：目标 × 地区的 7 天窗口汇总。
  - `entry_route_traces`：目标 × 运营商的最近一次 mtr 结果（每跳 ASN 序列、测量时间、measurement ID）。
  - 等级计算放在 SQL 函数里，Python 和 Worker 共用（与现有 catalog 函数相同的做法）。
  - 同步 `app/readiness.py`、Worker readiness 及相关测试。
- **容量**：每天约 12,000 条结果，保留 14 天约 17 万行，估计不超过 20 MB；纳入 `cleanup` 的保留预算。
- **三端一致**：`app/quality.py`、`cloudflare/api-worker/src/quality.ts`、`catalog.ts` 的筛选/排序允许列表与导出投影同步修改；新增等级字段进入 compact 列表的位置数组。
- **新密钥**：Globalping token 存为 GitHub Secret `GLOBALPING_TOKEN`；不写进 Variables、日志或 argv。
- **测试**：单元测试（档位边界、门槛、短板合成、CF/Hy2/IPv6 分支、样本不足）、真实 PG 集成测试（SQL 函数与 Worker 结果一致）、Globalping 客户端使用录制的合成响应；不对真实节点做测试测量。
- **前端测试**：`node --check` 所有改动的 JS；手机宽度（375 px）和深色主题下检查徽章与表格；20k 合成节点下切换视图和视角的耗时不劣于现状（见 STATUS 第四轮的基准）。
- **文档**：更新 QUALITY_AND_EXECUTION.md、STATUS.md；用户的覆盖决策写进 HANDOFF.md 的决策表。

## 8. 分阶段

1. **阶段 1：本体等级（不依赖第三方）。** 稳定性 + 落地标签 + 按落地服务器汇总 + 待定档。只用现有数据，接入档暂时全部显示“未测”，等级最高 B。不需要用户做任何新授权。
2. **阶段 2：接入层。** Globalping 接入、晚高峰调度、各地区等级、“该地区 TCP 不通”标记、三网去程路由。需要第 9 节的授权。

## 9. 需要用户决定

1. **第三方暴露。** Globalping 是公开网络：测量目标（入口 IP:端口）会发给社区运营的探针，拿到 measurement ID 的人能在约 6 个月内查到结果。这超出了目前“真实节点不出本系统”的边界。是否接受？
   - 补充选择：只发 IP（默认），还是也发域名。发域名能测出大陆 DNS 污染，但会暴露机场域名。
2. **覆盖既有决策。** 接管指南写的是“大陆可达性保持 UNKNOWN、分级只是理论候选”。阶段 2 会记录真实的大陆 TCP 实测结果和去程路由事实（仍不判断线路类型）。确认覆盖后写入决策表。
3. **注册一个 Globalping 账号**（免费），生成 token 存入仓库 Secret。不注册多个账号，不叠加匿名额度（见 4.4）。
4. 默认地区选哪个（例如 CN-CT），以及阶段 1 是否先做。
5. **界面移除 P1/P2/P3 理论等级和人工线路声明/优先级**（6.1、6.2、6.6）。按“只记录能实测证明的东西”的原则，它们会被新等级取代；数据库里的旧数据保留、不删除。

未获授权前，不对任何真实节点发起第三方测量；验证 API 时只使用 1.1.1.1:443 这类公共目标。
